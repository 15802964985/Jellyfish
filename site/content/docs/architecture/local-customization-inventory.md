# 本地二开能力清单

本文只记录 `local/stable-codex-0718` 当前真实生效的二开能力。详细文件、提交和迁移边界见仓库根目录的 `docs/Jellyfish-二次开发变更清单.md`。每次二开代码、数据库迁移、配置或用户流程发生变化，必须在同一提交中更新两份文档；上游升级时，不以“提交能否直接 cherry-pick”为判断标准，而以业务结果、数据契约和验收条件为迁移基线。

## 二开变更的同步规则

任何新增或调整二开能力都必须同时完成：

1. 更新本清单中对应领域、行为边界和验收条件。
2. 当前实现细节写入 `site/content/docs/architecture/`；尚未落地的事项写入 `site/content/docs/plans/`。
3. 用户操作、部署或配置发生变化时，同步更新 `docs/Jellyfish-中文版配置使用手册.md`。
4. API 或类型改变时，以后端 OpenAPI 为真值重新生成前端客户端，不手工拼接 generated 文件。
5. 数据结构改变时新增 Alembic revision，并记录升级、验证与回退边界。
6. 提交前记录对应测试；未完成文档同步的二开修改不视为完成。

## 上游升级的使用方式

升级前把本文每一行复制到“迁移决策台账”，逐项标记：

- `采用上游`：上游已经以相同或更好的方式完整满足结果，本地旧实现不再迁移。
- `保留本地`：上游没有等价能力，迁移本地实现并适配新架构。
- `兼容合并`：两边各有优势，保留上游结构并补齐本地缺口。
- `重新实现`：本地旧代码不适合新架构，只迁移业务意图、数据和测试。
- `淘汰`：本地代码已被上游替代、属于临时补丁或会恢复废弃链路。

台账必须给出上游证据、本地证据、最终决定、涉及文件/迁移/API、测试结果和文档更新，不能只写“已合并”。完整流程见 [上游更新与二开智能迁移 SOP](/docs/guide/upstream-upgrade-sop/)。

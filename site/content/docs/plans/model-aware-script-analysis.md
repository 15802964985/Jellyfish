## 实际代码差距

- 深度分析目前是完整 Schema 提示 + 普通消息调用 + 本地校验，不是自动采用原生 structured output。
- `runtime.py` 当前在关闭思考时统一加 `enable_thinking`；这是跨供应商参数风险，须按模型/协议拆分，不应未经核对就发给 OpenAI 或火山。
- 本地业务 schema 含动态 `attributes` 字典；严格 Schema 的供应商子集适配不能删掉属性信息或强行设置 additionalProperties=false 后丢失内容。
- 当前支持响应外壳差异不等于能可靠修复语义缺失；人物身份、镜头归属必须依赖原文证据，不能靠名称前缀猜测。

## 实施顺序与验收

1. 建立可更新能力清单：供应商、精确模型/已验证版本范围、端点类别（套餐/标准）、思考与流式约束、结构化模式、Schema 子集、来源 URL/核对日期/验证级别。未知能力明确 unknown，不推断为支持。
2. 调用前按该模型选择已验证的原生 Schema、JSON Object 或提示约束路径；不支持直接阻止或提示限制，禁止失败后偷偷切模型、换费用来源或再次外发。
3. 供应商协议适配与语义分析分离：模型理解原文，协议层负责消息/工具参数/拒绝/截断/错误；业务层统一证据与实体/镜头/音频关系。
4. 受控留存响应、免费重解析、待确认候选区、真实阶段进度沿用智能导入计划；任何额外语义修复调用需用户确认。
5. 离线测试覆盖五家供应商边界和每种协议模式；真实测试按当前已配置模型逐个取得授权。分别记录“文档确认”“Mock 通过”“真实调用通过”，不能用一种替代另一种。

禁止在每次用户生成时临时抓网页、自动按网页内容修改生产配置。文档核对是维护/升级流程，审核后更新版本化能力数据并回归，再进入正式调用。

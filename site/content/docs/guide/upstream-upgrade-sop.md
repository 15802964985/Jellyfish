# 上游更新与二开智能迁移 SOP

若本次只换电脑，先按 [新电脑部署与数据迁移](../../../../docs/Jellyfish-新电脑部署与数据迁移.md) 恢复同一精确代码/数据版本，验收后再独立升级；不要把搬迁与吸收上游同时进行。迁移电脑也要携带项目记忆和未关闭计划。

上下文接手先读当前根目录 [PROJECT_MEMORY.md](../../../../PROJECT_MEMORY.md) 及 AGENTS.md，再执行本文。候选目录迁移必须保留或智能合并项目记忆、AGENTS 接手规则及所引用的台账/计划；正式验收后更新记忆中的真实根目录、基线 SHA、部署证据、未关闭计划和下一步。不能把旧快照直接当新版本事实，也不能因采用上游 AGENTS.md 而丢失本地交接入口。

当用户下达“检查 GitHub 最新代码并同步更新”或同义指令时，默认执行本文流程。目标不是把旧提交机械套到新代码上，而是在作者最新可用分支上逐项审查本地能力，做采用、保留、兼容、重构或淘汰，并以数据安全和业务验收结果决定是否切换。

## 不可变原则

1. 当前生产目录 `E:\JellyfishNew` 在候选版本通过隔离验证前保持不变，不在其中直接 merge 上游。
2. 先确认作者真正的最新活跃分支和提交，不能永久假设 `main` 或 `codex/0718` 最新。
3. 代码、MySQL、RustFS 和部署配置先备份；备份不得进入 Git。
4. 新目录只从作者最新分支创建，二开能力逐项迁移，不用 ZIP 覆盖，也不批量选择 `ours`/`theirs`。
5. 上游已经更好解决的能力采用上游；本地临时补丁应删除；不能为减少冲突恢复作者已废弃的接口或架构。
6. 数据库先在隔离副本上迁移；未通过测试和还原检查，不碰当前业务库。
7. 切换后先验收和观察，再清理。删除旧目录、SQL/RustFS 备份属于破坏性终态操作，必须列出精确路径并取得人工确认。

## P0：发现和冻结范围

- 检查任务中心，等待或取消所有进行中、排队任务。
- 记录当前分支、HEAD、远程地址、容器状态、数据库 revision、关键表数量和文件对象数量。
- `git status --short` 必须为空；未提交修改先审查并形成提交，不把未知脏文件带入升级。
- 执行 `git fetch --all --prune`，比较作者各活跃分支的提交时间、共同祖先、发布标签、变更日志和 CI；把选定的 `upstream branch + commit SHA` 写入台账。
- 读取 [本地二开能力清单](/docs/architecture/local-customization-inventory/) 和根目录 `docs/Jellyfish-二次开发变更清单.md`，为每个 `LC-*` 已生效能力及每个未关闭 `PL-*` 计划创建迁移决策记录。

## P1：完整备份并验证可用性

以时间戳创建独立目录，例如 `E:\JellyfishBackups\20260904-120000`，至少保存：

- 当前代码 bundle/稳定分支与提交号；
- MySQL `--single-transaction --routines --triggers` 逻辑备份；
- RustFS 数据归档；
- `.env` 和安全 Compose 覆盖文件；
- 容器、镜像、卷、迁移 revision 和关键表计数清单。

备份后检查文件大小、校验和，并把 SQL 恢复到临时数据库做最小还原验证。仅仅看到备份文件存在不算可恢复。

## P2：在全新候选目录获取作者版本

候选目录使用时间戳，例如 `E:\JellyfishCandidate-20260904-120000`：

```powershell
$Stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$Candidate = "E:\JellyfishCandidate-$Stamp"
git clone --origin upstream https://github.com/Forget-C/Jellyfish.git $Candidate
Set-Location $Candidate
git fetch upstream --prune --tags
git switch --detach <P0确认的作者提交SHA>
git switch -c "integration/upstream-$Stamp"
```

复制配置前先比较新版 `.env.example` 和 Compose 参数。只迁移必要的本机值，不把旧 `.env` 整文件覆盖新配置，也不在日志中打印密钥。

## P3：逐项智能对比和迁移

对能力清单和未关闭计划逐项填写台账：

| 字段 | 要求 |
| --- | --- |
| 能力 | 使用清单中的稳定业务名称 |
| 上游现状 | 新代码是否完整、部分或未实现，附代码/测试证据 |
| 本地现状 | 对应提交、文件、迁移、API 和已知限制 |
| 决策 | 采用上游 / 保留本地 / 兼容合并 / 重新实现 / 淘汰 |
| 实施 | 最终落点、数据兼容、OpenAPI 和前端影响 |
| 验证 | 自动测试、运行烟测和人工场景 |
| 文档 | 清单、架构、计划、手册的同步位置 |

计划类条目还必须记录：已完成阶段、仍未完成阶段、阻塞/前置条件、作者新版覆盖情况，以及升级后继续、合并、重写、暂缓或取消的决定。

决策顺序：

1. 先比较业务结果和数据契约，再比较文件 diff。
2. 上游完整且更优时采用上游，只迁移缺失的测试、数据兼容或中文化。
3. 上游部分实现时，基于其新扩展点补齐本地能力。
4. 架构冲突时重新实现本地业务意图，不强行 cherry-pick 旧代码。
5. 双方都改数据库时保留双方 revision；出现多头就新增 Alembic merge revision。
6. 双方都改 API 时先定后端契约，再生成 OpenAPI 和前端客户端。
7. 对安全、权限、密钥和文件删除采用更严格的边界。

每迁移一个独立领域就提交一次，并在台账中关联提交。禁止一次提交混入全部冲突，避免无法审计和回退。

## P4：隔离验证候选版本

候选版本必须使用独立 Compose project、临时端口和由备份恢复出的临时数据库/对象存储，避免接触当前业务数据。依次通过：

1. 后端完整测试、lint/导入校验。
2. OpenAPI 重新生成且 generated client 无未解释差异。
3. 前端 TypeScript 检查和生产构建。
4. Alembic 从生产数据库副本升级成功，系统 seed 幂等，关键表数量不减少。
5. 后端、前端、Worker、Beat、MySQL、Redis、RustFS 健康；日志无迁移错误和持续 Traceback。
6. 项目/章节 CRUD 与分页、任务中心、剧本导入、模型目录与默认模型、提示词模板、素材上传/预览/复用、图片/视频任务创建和取消恢复完成烟测。
7. 付费模型调用默认只做用户批准的低成本样例；不能用“连接成功”代替任务链路验证。

任何一项失败都留在候选目录修复，不迁移当前业务库。

## P5：停机窗口和正式切换

- 再次确认无运行任务，创建最终增量备份并记录精确时间。
- 停止当前应用层服务，但不删除卷，不执行 `docker compose down -v`。
- 将已验证候选代码切换为正式的 `E:\JellyfishNew`，保持固定 Compose project 名和受控端口。
- 在当前数据库执行候选 Alembic migration 和幂等系统 seed，然后启动服务。
- 立即核对健康检查、Worker/Beat、迁移 revision、关键表数量及错误日志。

若正式迁移失败，停止继续操作，保留现场，根据迁移可逆性决定代码回切或经人工确认后恢复数据库；不得自行删表、删卷或覆盖备份。

## P6：正式验收和固化

至少完成 P4 的全部烟测，并额外确认历史项目、章节、模型、任务、文件和素材仍可访问。通过后：

- 更新本地稳定分支，创建带作者基线 SHA 的稳定标签并推送自己的 Fork；
- 更新迁移决策台账、二开能力清单、架构文档和中文版配置使用手册；
- 更新所有受影响的 `PL-*` 状态和来源计划，并从仍未关闭计划给出下一阶段优化顺序；
- 记录测试命令、结果、已知限制和回退点；
- 确认 `.env`、数据库/RustFS 备份和 API Key 未进入 Git。

## P7：人工确认后清理

先向用户列出准备删除的候选失败目录、旧代码目录和临时备份的绝对路径，并说明删除后无法本机恢复。只有同时满足以下条件才可请求清理确认：

- 新 `E:\JellyfishNew` 已完成正式验收和观察；
- 稳定分支与标签已推送，可恢复代码；
- 数据库迁移与业务数据数量已复核；
- 用户明确同意删除列出的备份。

确认后只删除清单中的精确目标，不使用模糊通配符，不删除 Docker 业务卷。清理完成后复核只剩一个正式代码目录和当前业务数据，并报告删除内容及其不可恢复性。

## 完成定义

只有“作者基线已记录、全部 `LC-*` 和未关闭 `PL-*` 已审计、迁移台账逐项关闭、自动测试通过、隔离迁移通过、正式环境验收通过、文档已同步、稳定分支/标签已固化、后续优化顺序已给出”全部满足，升级才算完成。备份尚未获准删除不代表升级失败，应明确报告为“升级已完成，清理待人工确认”。
